# Delegated Verification

## Flow

1. **Preflight (once per session)**: `subagent({action:"list", capabilities:true})` — the returned capability rows (each carrying the agent's description, tools, model and acceptance role) are authoritative for casting. Re-run only if `agents/` changed mid-session. A session keeps the `subagent` tool **declaration** it started with while `pinToolDeclarations` is true — the default since 0.78.0 (`docs/configuration.md:113`) — so a package upgrade reaches a running session's declaration only after a restart, or immediately with `pinToolDeclarations: false` at the cost of one prompt-cache miss. Capability rows are unaffected: they come from the live `agents/` at call time.

   **Fresh machine?** Dispatching before bootstrap wastes rounds: if a whitelisted skill path or the host package is missing, run `cd ~/.pi/agent/npm && npm install && npm run selftest` first — those invariants cover whitelist paths and host-package resolution. If `researcher`/`evidence-auditor` fail on a missing exa path, run `~/.pi/agent/scripts/clone-skill-repos.sh` first (sparse clone of `skills/` only, ~2MB rather than 857MB).
2. **Agent detail — escalate, never scan**: do **not** read `agents/*.md` (7 files, ~38KB) to cast. The capability row omits `systemPromptMode`, `inheritProjectContext`, `inheritGlobalContext` and `inheritSkills`; when you need one of those — or any other frontmatter field — call `subagent({action:"get", agent:"X"})` for that one agent only; it also returns the agent's `Path` and its full system prompt.
3. **Casting** (read-only by default): claim verification → `evidence-auditor`; directory/package recon → `scout`; use a writer agent only when the operator explicitly asks for modifications.
4. **Fan out once**: one async run with all verification tasks. Since 0.74.0 the script is **not** a tool parameter: write it as a single ` ```js workflow ` fenced block in the same reply as the call, then call `subagent({ workflow: true, ... })`. Since 0.76.0 a lone bare ` ```js ` block is accepted too, and a missing block fails with `workflow: true needs one fenced block in the same reply as the tool call, opened with the exact line " ```js workflow" and closed with " ```"; found N.` plus a file-fallback hint (`src/extension/reply-workflow-script.js:37,40` since 0.80.0). A string containing `/` is a script path (`workflow: "./script.js"`). Passing `workflowScript`/`workflowScriptPath` still throws at execute time (`src/extension/public-execution.js:3-4` messages, `:13-18` enforcement, path since 0.80.0). With `disabledFeatures: ["workflow-scripts"]` the tool instead takes `tasks: [{agent, task}, ...]` (parallel) or `chain: [...]` (sequential) — both measured in v0.74.0. Use stable independent keys and verb-phrase labels for the runs.
5. **Yield immediately**: no bg_wait, no polling; wake on the native completion notification.
6. **Reconcile conflicts first**: when a child's verdict conflicts with yours, trust the side with reproducible evidence; if still in doubt, re-check or re-run — don't split the difference.

## Child Prompt — Five Required Elements

- Objective + cwd + **read-only boundary** (be specific, e.g. "no chezmoi write operations")
- Claims listed and numbered (C1…Cn), each falsifiable
- Uniform verdict format: per-claim `CONFIRMED / REFUTED / PARTIAL` + evidence line → overall verdict
- Stop condition: halt and report if a write operation or boundary violation would be needed — do not expand scope on your own
- No `model` override for verification tasks (inherit the session model)
- For tasks expected to run long (multi-stage builds, wide recon): set `timeoutMs` sized to the task, and add one line — "send a one-line `progress_update` at each milestone". Heartbeats ride the child's context; the parent only receives event stubs. Never poll with `bg_wait`

| Applying a child's patch | Normalize hunk headers first; only apply after `git apply --check` passes (field data: raw apply succeeds ~1/5 mechanically; normalized 5/5) |

Execution-level acceptance → `verifier`/`delegate` + gate. Since 0.78.0 the built-in `reviewer`/`oracle`/`evidence-auditor` are not asked to end with an acceptance report unless `acceptance` is set (`agents/*.md` carry no such instruction; report mode resolved at `acceptance.js:124`), so an `acceptance`-less review leaves no child report for `/subagents-refine`. |
| Context | Default to `fresh` **unless** config `defaultSubagentContext` or an agent's `defaultContext` says otherwise; implicit fork falls back to `fresh` without a persisted parent + leaf. "Fork needs explicit `timeoutMs`/budget" is guidance, not enforced — explicit `context: "fork"` only requires a persisted parent session + current leaf (`src/shared/fork-context.js:100,104`) |
| Fan-out size | Estimate the count first: `maxSubagentSpawnsPerRun` is an all-or-nothing group admission — the check precedes any claim/file/child creation, so partial starts are structurally impossible and the error reads "No children from this admission group were started." | Gate semantics | Gate passing ≠ run passing (fail-only downgrade, `src/runs/background/subagent-runner.js:1187-1191`); failure blocks the verdict but does not delete produced artifacts (`acceptance.js` has no deletion path); `gate` + `acceptance` are mutually exclusive ("gate cannot be combined with acceptance; use one gate command or acceptance.verify.", `acceptance.js:186`). Also: `acceptance: false` with `gate` is allowed (treated as omitted, `acceptance.js:185`); `gate` is rejected with `action: "resume"` (`src/runs/foreground/subagent-executor.js:4565` since 0.80.0; retained resume `:4480`); a typed gate (`output: "json"`) cannot combine with `outputSchema` (`acceptance.js:174`, enforced via `describeTypedVerifyOutputSchemaConflict` at the same file's `:4576-4584`, called at `:7051` (0.80.0)) |

## Anti-patterns

- Nested async helpers inside the workflow script block (the sandbox rejects them); splitting a fan-out into multiple direct calls instead of one
- Attaching acceptance / toolBudget to read-only verification tasks
- Vague claims ("check if there are any problems") — must be numbered and falsifiable
- Writing lore into this skill without checking it against the current source: e.g. the retelling that "`resume` drops / doesn't inherit the toolBudget" is **wrong in mechanism but right in effect**, and the counter-retelling "that's refuted, resume restores `initialToolBudget`" is **an over-claim**. `async-resume.js` does restore the launch-time `initialToolBudget` (`toolBudget: descriptor.initialToolBudget`, v0.79.1:659 — inside `applySteeringRecoveryAgentConfig`, `:634`, `src/runs/background/async-resume.js`), but that object is then fed through `initialToolBudgetState()` (`src/runs/shared/tool-budget.js`:37, literal `toolCount: 0` at `:38`), which returns `toolCount: 0` — and `toolCount` is not among the resume descriptor's persisted fields (the `allowedFields` whitelist at v0.79.1:282-290 has `initialToolBudget` but no `toolCount`, even after gaining `runFanoutBudget`/`lane`/`baseRef`/`extensionBindings`/`requiredExtensions`/…). So the *counter* is re-armed and the resumed child gets the full original allowance again. The budget is not dropped, it is re-granted in full.

  **Do not generalize this to steering.** `remainingSteeringRecoveryLimits()` (function at `src/runs/background/steering.js`:210) legitimately subtracts consumption (`initialToolBudget.hard - consumed`, `:221`, block `:219-230`; measured: hard 10 − consumed 3 → hard 7, and consumed 10 throws "no remaining tool budget"). The reduced value reaches the recovery launch as `params.toolBudget` and takes precedence over the restored full budget (`src/runs/background/async-execution.js:1742-1743`) — that precedence is what keeps steering from re-granting. "Restored in full" is a statement about `resume` only.

  Every piece of lore must survive a source audit before landing here

## Wrap-up

Summary table (original claim × verdict × key evidence) → ask the operator for execution scope; for irreversible actions (deletion etc.), restate the scope and wait for one explicit confirmation even if already selected.
